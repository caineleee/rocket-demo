## 一、状态机与响应码重构

**Commit**: `ebca065 refactor(common,all-services): 状态机与响应码重构，拆分ShopCode为独立枚举+流转校验`

### 1.1 问题诊断

原 `ShopCode` 枚举混了三类语义：

| 语义类型 | 示例 | 用途 | 值范围 |
|----------|------|------|--------|
| DB 状态码 | `ORDER_PAY_STATUS_IS_PAY(2)` | 写入 tinyint 列 | 0/1/2/3 小值 |
| API 响应码 | `PAYMENT_IS_PAID(70002)` | 抛业务异常返回前端 | 70000+ 大值 |
| 业务类型标识 | `USER_MONEY_LOG_TYPE(1)` | 标识日志类型 | 0/1/2 |

弱类型导致"响应码当状态码写库"等事故能藏很久：

- `PaymentServiceImpl` 用 `PAYMENT_IS_PAID(70002)` 查 `is_paid` 列 → 永远查不到
- `OrdersServiceImpl` 用 `COUPON_ISUSED.getSuccess()` 拿布尔 `true` 当状态值写库
- `UserServiceImpl` 用 `ORDER_PAY_STATUS_IS_PAY(2)`（状态码）当响应码抛

这些误用靠 ShopCode 的弱类型藏了很久，超 tinyint 范围才暴露成 "Data truncation"。

### 1.2 改动内容

1. **拆分状态码为独立枚举**（`common.constant.status`）：
   - `OrderStatus` / `PayStatus` / `CouponStatus` / `MqMessageStatus` / `UserMoneyLogType`
   - 值小（0/1/2/3），专写库用

2. **新增 ResultCode**（`common.constant.code`）：
   - 独立响应码，`CastException.cast` / `CustomerException` / `Result` 只接收 `ResultCode`
   - 编译期就能防止"响应码当状态码写库"

3. **新增 StatusTransition 工具**（`common.statemachine`）：
   - 内置流转规则表，`check(from, to)` 校验非法流转
   - 非法流转抛 `IllegalStateException`（编程错误，不返回前端）

4. **新增 GlobalExceptionHandler**（`common.exception`）：
   - `@RestControllerAdvice` 统一异常 → `Result` JSON
   - 4 个 Handler：`CustomerException` / `MethodArgumentNotValidException` / `IllegalStateException` / `Exception`
   - `@ConditionalOnWebApplication(type = SERVLET)` 排除 Gateway（WebFlux）

5. **全量替换 13 个文件的 ShopCode 调用点**，修正历史误用：
   - 关键流转点加状态机 check：`updateOrderStatus`、`callbackPayment`、`OrderFailure`
   - `callbackPayment` 初始状态 `UNPAID→PAYING`，让 `PAYING→PAID` 合法

### 1.3 涉及文件

```
common/constant/ShopCode.java                    (删除)
common/constant/code/ResultCode.java             (新增)
common/constant/status/{OrderStatus,PayStatus,CouponStatus,MqMessageStatus,UserMoneyLogType}.java (新增)
common/statemachine/StatusTransition.java         (新增)
common/exception/{CastException,CustomerException,GlobalExceptionHandler}.java
common/model/Result.java
common/aspect/RedisAspect.java                   (ShopCode→ResultCode)
common/service/RedisOperationService.java        (ShopCode→ResultCode)
common/spel/SpelSecurityFilter.java              (ShopCode→ResultCode)
{order,pay,coupon,goods,user}-service/.../ServiceImpl.java  (全量替换调用点)
```

### 1.4 经验教训

- **类型隔离是最好的防御**：DB 状态码和 API 响应码混在一个枚举里，靠人盯总会漏；拆成强类型枚举后，编译器帮你拦
- **状态流转要校验**：非法状态跳转属于编程错误，应该 fail-fast（抛异常），不该静默写入脏数据
- **全局异常处理统一出口**：业务异常、校验异常、未知异常都走 `@RestControllerAdvice`，前端拿到的永远是标准 `Result` JSON

## 二、JWT 配置外部化 + 自动化脚本

**Commit**: `3a55809 refactor(config): JWT密钥与过期时间外部化到环境变量，新增.env自动检测脚本`

### 2.1 问题

1. **JWT 密钥硬编码**：`JwtConstants.SECRET_KEY = "rocket-demo-jwt-secret-key-2026"` 直接写在代码里，进 git 仓库存在泄露风险
2. **网段切换配置失效**：`.env` 中 `HOST_IP` / `NACOS_SERVER_ADDR` 在切换网段（如 192.168.31.x → 192.168.5.x）后需手动改，容易遗忘；RocketMQ broker 还用旧 IP 注册到 nameserver，导致宿主机侧 producer 拿到不可达地址，异步发送报 "unknown reason"

### 2.2 改动内容

1. **JwtConstants 移除硬编码**：
   - 删除 `SECRET_KEY` / `ACCESS_TOKEN_EXPIRE_TIME` / `REFRESH_TOKEN_EXPIRE_TIME`
   - 仅保留结构性常量（前缀、Header 名、Payload key、Redis key 前缀）

2. **JwtUtil 改读环境变量**：
   - `JWT_SECRET`（HMAC-SHA256 密钥，≥32 字节）、`JWT_ACCESS_EXPIRE`（默认 30 分钟）、`JWT_REFRESH_EXPIRE`（默认 7 天）
   - `parseLongEnv` 容错解析，未设置/格式非法时回退默认值

3. **TokenService** 的 Refresh Token 过期时间改用 `JwtUtil.getRefreshTokenExpireTime()`

4. **`.env` / `.env.example`** 新增 JWT 配置项

5. **新增 `scripts/update-env.sh`**：
   - 自动检测局域网 IP（`ipconfig getifaddr en0`）
   - 同步 `.env` 的 `HOST_IP` / `NACOS_SERVER_ADDR`
   - 解决切网段后连不上 broker 的问题

6. **新增 `scripts/dev-start.sh`**：
   - 统一启动脚本：IP 检测 → 加载 `.env` → 关闭 Docker Compose 自动管理 → 模块目录下 `mvn spring-boot:run`
   - 用法：`./scripts/dev-start.sh user-service` / `all`

### 2.3 目的

- 敏感配置不进代码库，可随环境注入（开发兜底值 / 生产强随机密钥）
- 网段切换一键同步，避免手动改漏导致连不上中间件

## 三、网关认证安全与 XSS 修复

**Commit**: `d632b71 fix(gateway-service): 修复登出后Token仍可用漏洞，优化XSS过滤器URI处理`

### 3.1 Bug：登出后 Token 仍可用

**现象**：`POST /user/logout` 返回 200，但之后用原 Token 请求 `/user/info` 仍返回 200。

**根因**：网关在转发非白名单请求时统一剥离了 `Authorization` 头（出于安全考虑，避免下游服务持有可用凭证）。但 `user-service` 的 `logout` 需要**读取 Access Token 才能将其加入 Redis 黑名单**。头被剥离后，登出"假成功"——返回 200 但 Token 没拉黑。

**修复**：对 `/user/logout` 路径特殊处理，保留 `Authorization` 头供下游读取并拉黑。

```java
boolean stripAuthorization = !"/user/logout".equals(path);
```

**验证**：登出后再请求 `/user/info` → 401 "Token has been blacklisted" ✅

### 3.2 优化：JWT 解析性能 + Redis 容错

1. **解析性能**：原 `getUserIdFromToken` + `getUserNameFromToken` 各解析一次（HMAC 验签跑两遍），改为 `parseToken` 一次取 `Claims`，减少一半 HMAC 计算
2. **Redis fail-open**：黑名单查询失败时放行（JWT 签名/过期已验证，风险仅限已登出 Token 短暂可用），避免 Redis 单点故障导致所有非白名单请求 500

### 3.3 Bug：XssGlobalFilter 破坏 URI

**根因**：用 `getQuery()`（已解码）获取 query，直接 HTML 转义后拼回 URI，单引号转义会破坏 URI 结构。

**修复**：改用 `getRawQuery()`（原始未解码），按 URL 解码 → HTML 转义 → URL 编码处理。

## 四、统一 System.out 为 SLF4J 日志

**Commit**: `d21beda refactor(common,gateway-service): 统一System.out为SLF4J日志，规范日志输出`

### 4.1 问题

多处 Servlet / Listener / Filter / Config 用 `System.out.println` 输出日志：

- 绕过 logback 框架，不受日志级别控制
- 不受 `totalSizeCap 200MB` 上限保护
- 异常时高频输出会撑爆磁盘（此前已发生过日志撑爆 20GB 的事故）

### 4.2 改动内容（14 个文件）

| 模块 | 文件 | 处理 |
|------|------|------|
| common filter | EncodingFilter、TimingFilter、CorsFilter | `@Slf4j`，`System.out→log.info` |
| common config | FilterConfig、ListenerConfig、ServletConfig | `@Slf4j`，注册日志 `log.info` |
| common servlet | FileDownloadServlet、ThirdPartyServlet、HealthServlet | `@Slf4j`，生命周期 `log.info`，高频请求 `log.debug` |
| common listener | AppStartupListener、SessionListener、ShutdownListener | `@Slf4j`，清理死代码块 |
| gateway | GatewayServiceApplication、CorsGlobalFilter | 启动横幅 `log.info`，OPTIONS `log.debug` |

**处理细节**：
- 字符串拼接 `+` 改为 SLF4J `{}` 占位符（日志级别关闭时避免无谓拼接，提升性能）
- 高频请求日志（HealthServlet.doGet、CorsGlobalFilter OPTIONS）用 `log.debug`
- **所有中文教育注释完整保留**（作者正在学习 Servlet/Filter/Listener）

### 4.3 目的

- 日志统一走 logback，受级别控制和 `totalSizeCap` 上限保护
- `{}` 占位符避免无谓字符串拼接，性能更好

## 五、MQ 消费者健壮性 + 并发安全

**Commit**: `b76d224 fix(all-services): MQ消费者异常处理与NPE防御，修复Demo并发安全问题`

### 5.1 MQ 消费者异常处理

**问题**：`OrderFailure` / `PaymentListener`（order-service）只 `catch (UnsupportedEncodingException)`，而 UTF-8 由 JLS 保证不会抛该异常。结果 JSON 解析失败、DB 异常、`CastException` 全部逃逸，消息被 ACK 丢失。

**修复**：
- `catch (UnsupportedEncodingException)` → `catch (Exception)`，抛 `RuntimeException` 触发应用层感知
- `new String(body, "UTF-8")` → `StandardCharsets.UTF_8`（去掉无用的受检异常）
- 失败日志 `log.info` → `log.error` 并传入异常对象，保留堆栈
- `OrderFailure`：订单查询结果 NPE 防御（`order` 为 null 时抛业务异常）
- `PaymentListener`：`order.getOrderStatus()` NPE 防御，改用 `Objects.equals`
- `MessageListener`（pay-service）：删除冗余 `System.out.println`

### 5.2 并发安全

**问题**：`RedisAopDemoController` 用 `HashMap` 作模拟缓存，Demo 接口可能被并发调用，多线程 `put` 会数据丢失或死循环（JDK7 链表成环）。

**修复**：`HashMap` → `ConcurrentHashMap`

## 六、配置修复

**Commit**: `fa03e51 chore(all-services): 配置外部化与修复（Sentinel env、worker-id、Dubbo重试、Mapper namespace）`

### 6.1 配置外部化

- **Sentinel Dashboard**：`localhost:8858` → `${SENTINEL_DASHBOARD:localhost:8858}`，支持环境变量覆盖
- **worker-id**：改为 `${ID_WORKER_ID:N}` 占位符，每个服务分配唯一值（user=1/goods=2/coupon=3/order=4/pay=5），避免 Snowflake ID 冲突

### 6.2 Dubbo 消费者配置

- **retries=0**：`reduceStock` / `reduceCoupon` / `updateMoneyPaid` 等扣减操作**非幂等**，超时重试会导致重复扣库存/扣券/扣款
- **timeout=3000**：默认 1 秒太短，DB 慢查询易超时

### 6.3 RocketMQ 消费者组

各服务使用独立 consumer group（如 `goods-order-cancel-group`、`order-order-cancel-group`），避免 BROADCASTING 模式下 offset 文件冲突。

### 6.4 Mapper XML namespace 修复

7 个 Mapper XML 的 namespace 去掉 `-service` 后缀：

```
coupon-service.mapper.CouponMapper  →  coupon.mapper.CouponMapper
```

与实际接口包路径对齐。

### 6.5 清理

删除 common 模块已废弃的 `XssFilter`（XSS 逻辑已迁移到 gateway-service 的 `XssGlobalFilter`，微服务侧不再注册）。

## 附：关键经验总结

1. **类型隔离优于约定**：DB 状态码 / API 响应码用独立强类型枚举，编译期拦截误用
2. **敏感配置不进代码库**：密钥、过期时间走环境变量，开发兜底 / 生产覆盖
3. **网段切换要自动化**：IP 检测脚本避免手动改漏导致连不上中间件
4. **日志走框架不走 stdout**：System.out 绕过 logback 不受控，统一 SLF4J
5. **非幂等操作禁重试**：Dubbo `retries=0`，防止扣减类操作重复执行
6. **MQ 消费者要 catch 全异常**：只捕获特定异常会让消息被 ACK 丢失
7. **增量编译可能漏报**：关键改动后用 `mvn clean compile` 强制全量编译
8. **common 改动要 install**：各服务独立 `mvn spring-boot:run` 用的是 `~/.m2` 里的 common jar，改完源码必须重新 `mvn install`
