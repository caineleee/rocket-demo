# 状态机与响应码重设计方案

> 状态：**待确认**（确认后再执行）
> 决策已定：① 状态机用「流转表 + 枚举」实现（轻量、零依赖）；② 全量改造并废弃 `ShopCode`

---

## 一、现状问题诊断

### 问题 1：三类语义混在一个 ShopCode 枚举里

`ShopCode` 同时承担了三种完全不同的职责：

| 语义 | 本应是什么 | 现在混在 ShopCode 里的例子 |
|------|-----------|--------------------------|
| **DB 状态码**（写进数据库列） | 各领域独立的状态枚举 | `ORDER_CONFIRM(1)`、`ORDER_PAY_STATUS_IS_PAY(2)`、`MQ_MESSAGE_STATUS_SUCCESS(1)` |
| **API 响应码**（返回前端/抛异常） | 统一的 `ResultCode` | `SUCCESS(1)`、`USER_NO_EXIST(30002)`、`REDIS_LOCK_ACQUIRE_FAIL(80001)` |
| **业务类型标识**（资金日志类型等） | 独立类型枚举 | `USER_MONEY_PAID(1)`、`USER_MONEY_REFUND(2)` |

**直接后果**：编译期无法区分，业务代码拿响应码当状态码写库 → 已发生实锤（见问题 7）。

### 问题 2：`success` 布尔字段语义双关、被误用

```java
public enum ShopCode {
    SUCCESS(true, 1, "正确"),           // success=true 表示「成功响应」
    ORDER_CONFIRM(true, 1, "订单已确认"), // success=true 被借用来表示「这是状态码」
    USER_MONEY_REFUND_ALREADY(true, 30004, "订单已经退过款"), // 错误信息却标 true，矛盾！
}
```

业务代码里已经出现两种误用：
- 用响应码当状态码写库：`pay.setIsPaid(ShopCode.PAYMENT_IS_PAID.getCode())` → 70002 写进 tinyint → Data truncation（已修复）
- 用 `getSuccess()` 布尔当状态值写库：`coupon.setIsUsed(ShopCode.COUPON_ISUSED.getSuccess())` → 写入 `true`

### 问题 3：命名和注释错误

| 枚举 | 注释 | 实际语义 |
|------|------|---------|
| `ORDER_PAY_STATUS_NO_PAY` | "订单已付款" | 实际是**未付款** |
| `ORDER_CANCEL(false, 2)` | "订单已取消" | 对 |
| `ORDER_INVALID(false, 3)` | "订单已取消" | 实际是**无效**，注释抄错 |
| `ORDER_SHIPPINGFEE_INVALID` | "快递运费不正确" | 实际是**订单运费** |

### 问题 4：订单状态与支付状态耦合

`Order` 实体有 `orderStatus` + `payStatus` 两个**正交维度**，`Payment` 实体有 `isPaid`，三个状态机却共用同一套 `ORDER_*` / `ORDER_PAY_STATUS_*` 枚举，容易混淆。

### 问题 5：没有状态机概念，流转规则散落

状态流转规则散落在业务代码的 `if/set` 里，没有集中定义，也**不校验非法流转**：
- 已取消的订单能不能再确认？代码没拦
- 未付款的订单能不能直接设已退款？代码没拦

### 问题 6：枚举可变性

`ShopCode` 的 `success/code/message` 都加了 `@Setter`，枚举值本应不可变。

### 问题 7：实锤 —— 支付回调 500

`callbackPayment` 里 `pay.setIsPaid(ShopCode.PAYMENT_IS_PAID.getCode())` 把响应码 70002 当状态码写入 `tinyint(1)` 列 → MySQL 报 `Data truncation: Out of range value`。这是问题 1 的直接后果，编译器没拦住。

---

## 二、设计目标

1. **状态码与响应码物理隔离**：分属不同类型，编译期就能防误用
2. **每个领域独立状态枚举**：订单、支付、MQ、优惠券、资金各自管理
3. **流转规则集中、可校验**：非法流转在运行期被拦截
4. **枚举不可变**：去掉 `@Setter`
5. **向后兼容可控**：全量替换 `ShopCode` 的调用点，一次性彻底
6. **零新依赖**：流转表用枚举自带方法实现，不引入框架

### 3.2 各领域状态枚举设计

每个状态枚举：不可变（无 Setter）、带 `code` + `desc`、内置 `canTransitionTo()` 描述合法流转。

#### OrderStatus（订单主状态机）

```java
package org.lee.rocket.train.common.constant.status;

import lombok.Getter;

/**
 * 订单状态机（写入 tb_order.order_status 列）
 *
 * 流转链路：
 *   NO_CONFIRM(0) ──确认──→ CONFIRMED(1)
 *   CONFIRMED(1)  ──取消──→ CANCELLED(2)
 *   CONFIRMED(1)  ──退货──→ RETURNED(4)
 *   任意非法流转 → 抛 IllegalStateException
 */
@Getter
public enum OrderStatus {

    NO_CONFIRM(0, "待确认"),
    CONFIRMED(1, "已确认"),
    CANCELLED(2, "已取消"),
    INVALID(3, "无效"),
    RETURNED(4, "已退货");

    private final int code;
    private final String desc;

    OrderStatus(int code, String desc) {
        this.code = code;
        this.desc = desc;
    }

    /** 当前状态是否可以流转到目标状态 */
    public boolean canTransitionTo(OrderStatus target) {
        return switch (this) {
            case NO_CONFIRM -> target == CONFIRMED || target == INVALID;
            case CONFIRMED -> target == CANCELLED || target == RETURNED;
            // 终态，不可再流转
            case CANCELLED, INVALID, RETURNED -> false;
        };
    }

    public static OrderStatus of(int code) {
        for (OrderStatus s : values()) {
            if (s.code == code) return s;
        }
        throw new IllegalArgumentException("未知订单状态码: " + code);
    }
}
```

#### PayStatus（支付状态机，Order.payStatus 和 Payment.isPaid 共用）

```java
package org.lee.rocket.train.common.constant.status;

import lombok.Getter;

/**
 * 支付状态机（写入 tb_order.pay_status 和 tb_payment.is_paid 列）
 *
 * 流转链路：
 *   UNPAID(0) ──发起支付──→ PAYING(1)
 *   PAYING(1) ──支付成功──→ PAID(2)
 *   PAID(2)   ──退款────→ REFUNDED(3)
 */
@Getter
public enum PayStatus {

    UNPAID(0, "未支付"),
    PAYING(1, "支付中"),
    PAID(2, "已支付"),
    REFUNDED(3, "已退款");

    private final int code;
    private final String desc;

    PayStatus(int code, String desc) {
        this.code = code;
        this.desc = desc;
    }

    public boolean canTransitionTo(PayStatus target) {
        return switch (this) {
            case UNPAID -> target == PAYING;
            case PAYING -> target == PAID;
            case PAID -> target == REFUNDED;
            case REFUNDED -> false;
        };
    }

    public static PayStatus of(int code) {
        for (PayStatus s : values()) {
            if (s.code == code) return s;
        }
        throw new IllegalArgumentException("未知支付状态码: " + code);
    }
}
```

### 3.4 状态流转校验工具

一个轻量工具类，集中校验流转合法性：

```java
package org.lee.rocket.train.common.statemachine;

import org.lee.rocket.train.common.constant.status.OrderStatus;
import org.lee.rocket.train.common.constant.status.PayStatus;

/**
 * 状态机校验工具
 * 用法：StatusTransition.check(OrderStatus.NO_CONFIRM, OrderStatus.CONFIRMED);
 * 非法流转直接抛 IllegalStateException，避免脏数据
 */
public final class StatusTransition {

    private StatusTransition() {}

    public static OrderStatus check(OrderStatus from, OrderStatus to) {
        if (!from.canTransitionTo(to)) {
            throw new IllegalStateException(
                "非法订单状态流转: " + from.getDesc() + "(" + from.getCode() + ")"
                + " -> " + to.getDesc() + "(" + to.getCode() + ")");
        }
        return to;
    }

    public static PayStatus check(PayStatus from, PayStatus to) {
        if (!from.canTransitionTo(to)) {
            throw new IllegalStateException(
                "非法支付状态流转: " + from.getDesc() + "(" + from.getCode() + ")"
                + " -> " + to.getDesc() + "(" + to.getCode() + ")");
        }
        return to;
    }
}
```

### 3.5 配套改造（CastException / Result）

**CastException**：`cast` 参数从 `ShopCode` 改为 `ResultCode`：

```java
public class CastException {
    public static RuntimeException cast(ResultCode code) {
        log.error(code.toString());
        throw new CustomerException(code);
    }
}
```

**Result**：构造器改用 `ResultCode`，去掉对 `success` 布尔的依赖：

```java
public class Result<T> implements Serializable {
    private String code;
    private Boolean success;   // 保留以兼容前端现有协议（code=="200" 时为 true）
    private String message;
    private T data;

    public Result(ResultCode rc) {
        this.code = String.valueOf(rc.getCode());
        this.success = (rc == ResultCode.SUCCESS);
        this.message = rc.getMessage();
    }

    public static <T> Result<T> success(T data) { return new Result<>("200", true, "操作成功", data); }
    public static <T> Result<T> success()       { return new Result<>("200", true, "操作成功", null); }
    public static <T> Result<T> fail(ResultCode rc) { return new Result<>(rc); }
}
```

> `success` 字段保留是为了兼容前端协议（前端按 `success` 判断），但其值改由 `code == 200` 推导，不再独立维护，彻底消除「布尔字段语义双关」。

**改造后**（类型安全 + 流转校验）：
```java
private void updateOrderStatus(Order order) {
    OrderStatus from = OrderStatus.of(order.getOrderStatus());
    OrderStatus to = OrderStatus.CONFIRMED;
    StatusTransition.check(from, to);                              // 非法流转直接抛异常
    order.setOrderStatus(to.getCode());
    order.setPayStatus(PayStatus.UNPAID.getCode());
    updateById(order);
}

private Long savePreOrder(Order order) {
    order.setOrderStatus(OrderStatus.NO_CONFIRM.getCode());        // 初始状态
    order.setPayStatus(PayStatus.UNPAID.getCode());
    ...
}
```

### 影响文件清单

| 类别 | 文件 | 改动 |
|------|------|------|
| **新增** | `common/constant/status/*.java`（5 个状态枚举） | 新建 |
| **新增** | `common/constant/code/ResultCode.java` | 新建 |
| **新增** | `common/statemachine/StatusTransition.java` | 新建 |

| **改造** | `common/exception/CustomerException.java` | 内部 ShopCode→ResultCode |
| **改造** | `common/model/Result.java` | 构造器 ShopCode→ResultCode |
| **替换调用** | `OrdersServiceImpl.java` | 所有 ShopCode 引用 |
| **替换调用** | `PaymentServiceImpl.java` | 所有 ShopCode 引用 |
| **替换调用** | 其余所有 `CastException.cast(ShopCode.XXX)` / `new Result<>(ShopCode.XXX)` | 全量替换 |
| **删除** | `common/constant/ShopCode.java` | 最后删除 |

### 执行步骤

1. **新增**状态枚举 + ResultCode + StatusTransition（不动现有代码）
2. **改造** CastException / CustomerException / Result（支持 ResultCode，同时保留 ShopCode 构造以便编译通过）
3. **批量替换**所有业务代码的 `ShopCode.XXX` 调用（状态码→状态枚举，响应码→ResultCode，流转处加 `StatusTransition.check`）
4. **验证**：各服务能编译通过 + 接口功能正常（复用之前的接口测试）
5. **删除** ShopCode.java，移除 CastException/Result 里的 ShopCode 兼容构造

### 风险与对策

- **风险**：调用点分散，漏改会导致编译失败（这是好事，能被编译器揪出来，不像 ShopCode 时代能误用却编译通过）
- **对策**：状态码改枚举后，类型从 `Integer` 传入变为 `枚举.getCode()`，漏改会直接编译报错 → 全量替换的可靠性反而比 ShopCode 高
- **风险**：响应码值变化（如 SUCCESS 从 1 改成 200）
- **对策**：ResultCode 保留原有分段码值，SUCCESS 特殊处理（前端协议用 "200"），改动前先确认前端依赖

## 六、对比总结

| 维度 | 现状（ShopCode） | 改造后 |
|------|-----------------|--------|
| 状态码与响应码 | 混在一个枚举，编译期不区分 | 物理隔离，不同类型 |
| 误用防护 | 无（响应码能当状态码写库） | 编译期拦截（类型不同） |
| 流转校验 | 无，散落 if/set | 集中流转表，非法流转抛异常 |
| 布尔字段 | success 语义双关被误用 | 去除，由 code 推导 |
| 可变性 | @Setter 可变 | 不可变 |
| 扩展性 | 加状态要改大枚举 | 加在自己领域枚举里 |
